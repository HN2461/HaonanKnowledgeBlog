## 一、四大扩展机制对比矩阵

### 1.1 核心属性对比

| 属性 | Rules | MCP | Skill | Plugin |
|------|-------|-----|-------|--------|
| **本质** | 静态规范文本 | 工具连接协议 | 任务流程模板 | 能力打包集合 |
| **包含内容** | Markdown 文本 | 服务器配置 + 工具定义 | 1 个 SKILL.md + 辅助资源 | Skills + Commands + Hooks + Agents + MCP |
| **生效方式** | 每次会话自动加载 | Agent 按需调用 | 按触发条件激活 | 安装后所有能力可用 |
| **持久性** | 持久 | 持久 | 持久 | 持久 |
| **分享范围** | Git 提交共享 | 配置文件共享 | 无法对外发布 | Marketplace 分享 |
| **安装方式** | 放到项目目录 | 配置连接地址 | 手动放目录 | 一行命令安装 |
| **版本管理** | Git 管理 | 手动维护 | 无原生支持 | 语义化版本 |
| **跨项目复用** | 全局个人配置可用 | 配置文件可复用 | 手动复制 | 安装一次全局可用 |
| **类比** | 员工手册 | 电话簿 + 工具箱 | 操作菜谱 | 技能套装包 |

### 1.2 解决的问题对比

| 问题 | 最适合的机制 |
|------|------------|
| AI 每次都忘了项目规范 | Rules（CLAUDE.md / AGENTS.md） |
| AI 需要查询外部系统信息 | MCP |
| 重复性多步骤操作 | Skill |
| 多种能力需要统一打包分发 | Plugin |
| 团队成员开发环境不一致 | Plugin（统一安装） |
| 只在特定任务里触发的流程 | Skill |
| 总是要生效的约束 | Rules |
| 需要连接数据库 / API / 浏览器 | MCP |

## 二、选型决策树

当你面对一个需求时，按以下决策路径选择最合适的机制：

```text
需求是什么？
│
├─ 是"告诉 AI 每次都要遵守的规则"？
│  └─ ✅ 用 Rules（CLAUDE.md / AGENTS.md / .cursor/rules）
│
├─ 是"让 AI 连接外部服务"？
│  └─ ✅ 用 MCP
│
├─ 是"一个特定任务的完整流程"？
│  ├─ 只在一个项目用，不需要分享？
│  │  └─ ✅ 用 Skill
│  └─ 需要跨项目 / 团队 / 社区分享？
│     └─ ✅ 做 Plugin
│
├─ 是"多种能力的组合"？
│  └─ ✅ 做 Plugin
│
└─ 不确定？
   └─ 先用最简单的：Rules → Skill → MCP → Plugin
```

### 简化判断口诀

> **规范写 Rules，连外用 MCP，流程写 Skill，打包做 Plugin。**

## 三、按工具选型速查

不同工具对四大机制的支持程度不同，选型时需要考虑你当前使用的工具：

### 3.1 Codex 选型速查

| 需求 | 推荐 |
|------|------|
| 项目规范 | `AGENTS.md`（项目根目录） |
| 个人偏好 | `~/.codex/AGENTS.md` |
| 连接外部服务 | MCP |
| 单一任务流程 | `~/.codex/skills/` |
| 多能力打包分发 | Plugin（`/plugin install`） |
| 团队统一工具链 | 项目级 Marketplace + Plugin |

### 3.2 Claude Code 选型速查

| 需求 | 推荐 |
|------|------|
| 项目规范 | `CLAUDE.md`（项目根目录 / `.claude/`） |
| 个人偏好 | `~/.claude/CLAUDE.md` + Auto Memory |
| 连接外部服务 | MCP |
| 快捷命令 | `.claude/commands/*.md` |
| 单一任务流程 | Skill |
| 多能力打包分发 | Plugin（`/plugin install`） |
| 自动化钩子 | Hooks（settings.json） |
| 并行任务 | Subagent |

### 3.3 Cursor 选型速查

| 需求 | 推荐 |
|------|------|
| 项目规范 | `.cursor/rules` + 根目录 `AGENTS.md` |
| 连接外部服务 | MCP |
| 任务流程 | `.cursor/rules`（Agent Requested 类型） |
| 多能力组合 | ❌ 无独立 Plugin，组合 Rules + MCP |
| VS Code 生态 | VS Code 扩展 |

### 3.4 Windsurf 选型速查

| 需求 | 推荐 |
|------|------|
| 项目规范 | `.windsurf/rules/*.md` |
| 连接外部服务 | MCP |
| 任务流程 | Skills + Workflows |
| 多能力组合 | ❌ 无独立 Plugin，组合 Rules + Skills + MCP |

### 3.5 Kiro 选型速查

| 需求 | 推荐 |
|------|------|
| 项目规范 | `.kiro/steering/*.md` |
| 连接外部服务 | MCP |
| 任务流程 | `.kiro/skills/` |
| 规格驱动 | `.kiro/specs/` |
| 多能力组合 | ❌ 无独立 Plugin，组合 Skills + Hooks + MCP |

## 四、没有 Plugin 体系时的替代方案

Cursor / Windsurf / Kiro 当前没有独立的 Plugin 体系，但可以通过组合其他机制实现类似效果：

### 4.1 替代方案 1：Rules + MCP 组合

```text
# .cursor/rules/ (Cursor)
├── always.mdc              # 始终生效的规则（= Rules 部分）
├── component-gen.mdc       # 组件生成流程（= Skill 部分）
└── deploy-check.mdc        # 部署前检查（= Hook 部分）
```

配合 `.cursor/mcp.json` 提供 MCP 工具连接。

### 4.2 替代方案 2：项目级模板仓库

创建一个模板仓库，团队成员 clone 后直接获得：

```text
project-template/
├── .cursor/rules/          # Cursor 规则
├── .windsurf/rules/        # Windsurf 规则
├── .kiro/steering/         # Kiro Steering
├── .kiro/skills/           # Kiro Skills
├── .cursor/mcp.json        # MCP 配置
└── setup.sh                # 初始化脚本
```

### 4.3 替代方案 3：共享 MCP 服务器

团队搭建共享 MCP 服务器，所有成员配置连接同一个服务，实现工具能力的统一分发。

## 五、团队协作策略

### 5.1 小团队（3-5 人）

| 机制 | 推荐做法 |
|------|---------|
| Rules | 项目根目录 `AGENTS.md`，提交到 Git |
| MCP | 共享一份 `.mcp.json` 模板，每人按需配置 token |
| Skill | 项目级 `.kiro/skills/` 或 `.cursor/rules` |
| Plugin | Codex / Claude Code 用户可直接用，其他工具暂不适用 |

### 5.2 中型团队（5-20 人）

| 机制 | 推荐做法 |
|------|---------|
| Rules | `AGENTS.md` + 各工具原生规则 |
| MCP | 搭建团队共享 MCP 服务器，统一 token 管理 |
| Skill | 模板仓库 + Code Review 流程 |
| Plugin | 项目级 Marketplace + 自研 Plugin |

### 5.3 大型团队 / 企业（20+ 人）

| 机制 | 推荐做法 |
|------|---------|
| Rules | 组织级 `AGENTS.md` + 项目级覆盖 |
| MCP | 企业级 MCP 网关 + 权限审批 + 审计日志 |
| Skill | 内部 Skill 库 + 版本管理 |
| Plugin | 内部 Marketplace + 审核 + 安全扫描 |

## 六、常见误区与避坑

### 6.1 误区：所有东西都做成 Plugin

**问题**：把一条简单规则也做成 Plugin，反而增加了维护成本。

**正确做法**：先判断是否需要打包和分发。如果只是一个简单规则，直接写 Rules 就够了。

### 6.2 误区：Plugin 能跨工具通用

**问题**：Codex Plugin 和 Claude Code Plugin 的清单格式、目录结构、命令体系都不同。

**正确做法**：Plugin 是"打包层"，内容逻辑可以复用，但文件形态需要按工具分别落地。和 Skill 的跨工具策略一样——**先写可移植内容，再按工具补专属层。**

### 6.3 误区：有了 Plugin 就不需要 Rules / MCP / Skill 了

**问题**：Plugin 是打包和分发机制，不是能力替代。

**正确做法**：Plugin 里面装的就是 Skills / Commands / Hooks / MCP。理解每种能力的本质，才能正确选择是单独使用还是打包成 Plugin。

### 6.4 误区：Codex Plugin 的 Marketplace 已经完全可用

**问题**：截至 2026-05-23，社区 Marketplace 尚未开放，社区插件只能通过本地路径安装。

**正确做法**：官方预装插件（Documents / Presentations / Spreadsheets）可以放心使用；社区插件暂时走本地路径安装，关注官方 Marketplace 开放动态。

### 6.5 误区：Cursor / Windsurf / Kiro 有 Plugin

**问题**：这三个工具有丰富的扩展能力（Rules + Skills + MCP），但没有独立的"Plugin"打包和分发机制。

**正确做法**：用 Rules + Skills + MCP 的组合来实现类似效果，不要等"官方出 Plugin"。

## 七、四大机制组合实战示例

### 7.1 前端项目完整配置

```text
my-project/
├── AGENTS.md                    # [Rules] 项目规范
├── CLAUDE.md                    # [Rules] Claude Code 专属规则
├── .cursor/rules/               # [Rules] Cursor 专属规则
│   ├── always.mdc
│   └── component-gen.mdc
├── .kiro/steering/              # [Rules] Kiro Steering
│   └── product.md
├── .kiro/skills/                # [Skill] Kiro 技能
│   └── component-gen/
│       └── SKILL.md
├── .mcp.json                    # [MCP] 外部工具连接
│   # GitHub、Figma、Notion 等
└── .claude/plugins/             # [Plugin] Claude Code 插件
    └── frontend-toolkit/
        ├── commands/
        ├── agents/
        ├── hooks/
        └── plugin.json
```

### 7.2 团队统一配置分发

1. 创建模板仓库，包含所有工具的规则和配置
2. 新项目从模板仓库初始化
3. Codex / Claude Code 用户额外安装团队 Plugin
4. 配置变更通过 Git 提交通知全团队

## 八、总结：选型核心原则

1. **从简单到复杂**：先 Rules，再 Skill / MCP，最后 Plugin
2. **按需求选机制**：规范写 Rules，连外用 MCP，流程写 Skill，打包做 Plugin
3. **按工具做适配**：Codex / Claude Code 可以做 Plugin，其他工具组合 Rules + Skills + MCP
4. **内容可复用，形态要适配**：逻辑可以跨工具复用，但文件形态按工具落地
5. **关注生态成熟度**：Plugin 生态还在快速演进，不要把不稳定的特性当成默认事实
