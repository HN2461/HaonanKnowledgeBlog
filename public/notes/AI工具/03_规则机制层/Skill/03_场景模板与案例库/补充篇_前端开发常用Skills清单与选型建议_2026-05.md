# 补充篇：前端开发常用 Skills 清单与选型建议（2026-05复核）

复核日期：2026-05-24

这篇只回答一个很实际的问题：

**如果你是前端开发，想给 AI 编码助手补一套真正高频、真正常用的 skills，到底优先做哪些。**

我这次整理时，重点看了 5 件事：

1. 这个 skill 是否真的贴近前端日常，而不是“听起来很高级”
2. 它更像长期规则，还是更像按需触发的任务流程
3. 它是否适合做成 skill，而不是更应该写进 `AGENTS.md` / `CLAUDE.md` / `Rules`
4. 当前官方文档能不能确认 Kiro / Cursor / Claude / Codex 都支持这类 skills 机制
5. 是否已经有现成可参考实现，还是更适合团队自己做

先给结论：

1. 如果主人主要做页面实现和样式落地，最值得先用的是 `frontend-design`
2. 如果主人经常要“真实跑一遍页面再确认”，最值得先用的是 `browser`
3. 如果主人最常遇到的是移动端错位、弹层遮挡、布局崩坏，最值得优先自定义的是 `responsive-debug`
4. 如果主人在做组件库、设计系统或企业后台，`accessibility-audit` 和 `component-patterns` 非常值得长期保留
5. 如果项目已经开始变大，`performance-audit` 会越来越值钱

## 一、先分清两类：现成可用 vs 更适合自己做

很多人一看 skills，就想先搜“有没有别人现成写好的”。

这当然没错，但对前端来说，更稳的思路其实是：

1. **现成可用的 skill**，优先拿来做通用能力
2. **项目强相关的 skill**，自己做一份更划算

原因很简单：

前端的大量问题都和下面这些东西强绑定：

1. 你们自己的组件命名和目录结构
2. 你们自己的样式体系
3. 你们自己的交互标准
4. 你们自己的路由、构建、发布和验收流程

所以真正高频、真正好用的前端 skill，往往不是“网上抄一个就结束”，而是：

**拿现成 skill 当母版，再按项目改成自己的版本。**

## 二、前端开发最值得优先关注的 6 类 Skills

| Skill | 类型 | 最适合的前端场景 | 推荐级别 | 我的建议 |
| --- | --- | --- | --- | --- |
| `frontend-design` | 现成可参考 | 页面实现、组件落地、样式重构、视觉提升 | S | 先看 |
| `browser` | 现成可参考 | 真机验收、查 DOM、复现交互、截图取证 | S | 先看 |
| `responsive-debug` | 强烈建议自定义 | 移动端错位、溢出、弹层遮挡、sticky/fixed 冲突 | S | 自己做 |
| `accessibility-audit` | 强烈建议自定义 | 语义结构、键盘可达性、焦点管理、ARIA 审查 | A | 自己做 |
| `component-patterns` | 强烈建议自定义 | 组件库、设计系统、统一 props / slots / 命名约定 | A | 自己做 |
| `performance-audit` | 强烈建议自定义 | 首屏慢、包体大、列表卡顿、CLS/LCP、资源浪费 | A | 中大型项目必备 |

如果主人只想先记一套最省心的组合，我建议就是这 4 个：

1. `frontend-design`
2. `browser`
3. `responsive-debug`
4. `component-patterns`

## 三、逐个推荐

## 3.1 `frontend-design`

- 类型：现成可参考的通用前端 skill
- 最适合：页面实现、组件样式、视觉提升、活动页、后台界面、落地页
- 当前最容易确认的参考：Codex 本地 skills 里的 `frontend-design`

### 为什么它适合前端

很多前端 skill 其实只会教模型“把页面写出来”，但 `frontend-design` 这类 skill 的价值更大，它会把下面几层一起打包：

1. 页面视觉方向
2. 排版与间距
3. 动效与交互细节
4. 实现时的技术约束

这很适合下面这些场景：

1. 主人要快速起一个新页面
2. 主人觉得现有界面“能用，但不够顺眼”
3. 主人想把一个业务模块从“工程能跑”推进到“交付能看”

### 它最值钱的点

不是“帮你写 HTML/CSS”。

而是让 agent 在开写之前，先把下面这件事想清楚：

**这个页面到底应该走什么审美方向、什么信息层级、什么交互气质。**

对前端来说，这比单纯多几个 CSS 片段更有用。

### 我怎么建议用

1. 先把它当“页面实现母版”
2. 再结合你们项目里的真实组件、主题变量、字号体系去约束它
3. 不要把它当“设计系统规范”，那部分更适合单独拆 skill

## 3.2 `browser`

- 类型：现成可参考的浏览器自动化 skill
- 最适合：真实页面验证、交互复现、控制台检查、截图、DOM 查询
- 当前最容易确认的参考：Codex 本地 skills 里的 `browser`

### 为什么它适合前端

前端最常见的一类误区是：

1. 代码看起来没问题
2. 组件逻辑看起来也合理
3. 但浏览器里实际就是不对

所以一个真正好用的前端 skill，不能只会“改代码”，还得会：

1. 打开页面
2. 触发交互
3. 看渲染结果
4. 检查 DOM、控制台、网络错误

这类能力对前端非常关键。

### 我最推荐的场景

1. 修复某个按钮点了没反应
2. 检查弹窗、抽屉、Popover、Tooltip 的实际显示
3. 做改版前后截图对比
4. 在真实页面里确认是不是样式、脚本或异步数据导致的问题

### 它和 MCP 的边界

这里也顺手提醒一句：

- `browser` skill 更偏**执行和验收流程**
- 浏览器类 MCP 更偏**把浏览器能力暴露成可调用工具**

两者经常能一起用，但不是同一个东西。

## 3.3 `responsive-debug`

- 类型：前端最值得自定义的一类 skill
- 最适合：移动端布局错位、内容溢出、弹层遮挡、窄屏断行、sticky/fixed 冲突

### 为什么我把它排到这么靠前

因为前端日常里，这类问题的出现频率真的太高了。

而且它们的共同特点是：

1. 不是简单搜一个 API 就能解决
2. 也不是只靠“代码审查”就能一眼看出来
3. 很依赖排查顺序

一个好的 `responsive-debug` skill，最重要的不是“列一堆 CSS 属性”，而是固定排查路径，比如：

1. 先确认复现页面和断点
2. 再看最小相关模板与父级布局链
3. 再看 `width`、`min-width`、`overflow`、定位、堆叠上下文
4. 最后才改代码

### 适合哪些前端

1. 常做移动端页面
2. 常做后台系统
3. 常做详情页和内容页
4. 常碰 Teleport / Portal / fixed header / sticky toolbar

如果主人后面真的要自己做前端 skill，我会把这个排到第一优先级。

## 3.4 `accessibility-audit`

- 类型：非常值得保留的质量型 skill
- 最适合：语义结构、键盘导航、焦点管理、标签命名、表单和弹窗审查

### 为什么前端要专门保留它

因为可访问性问题和普通视觉 bug 不太一样。

它们经常是：

1. 页面肉眼看起来正常
2. 鼠标点起来也没问题
3. 但键盘、读屏器或低视觉依赖场景下就出错

例如：

1. 按钮没有可访问名称
2. 弹窗打开后焦点丢失
3. 图标全靠颜色区分状态
4. 用 `div` 假装按钮

这种问题，如果没有专门的 checklist，很容易一直漏。

### 我更建议谁优先做

1. 做企业后台的前端
2. 做表单重、弹窗多、交互复杂的前端
3. 做组件库的前端

## 3.5 `component-patterns`

- 类型：团队前端最值得自定义的一类 skill
- 最适合：组件库、设计系统、统一命名、统一 props / slots / emits / hooks 约束

### 为什么这类 skill 很值钱

因为前端团队最容易出现的，不是“没人会写组件”，而是：

1. 每个人都能写
2. 但每个人写法都不一样

这就很适合 skill。

它可以把下面这些“总在重复说”的约束，沉淀成按需流程：

1. 什么时候拆容器组件和展示组件
2. props 命名怎么统一
3. 什么时候允许透传属性
4. 什么时候必须补空态、加载态、错误态
5. 什么时候该复用基础组件而不是新造一个

### 它和 `AGENTS.md` 的边界

这一类最容易和长期规则混在一起。

我更建议这样分：

- 总是要生效的底层规范，写进 `AGENTS.md` / `Rules`
- 真正带步骤、带判断、带示例的组件实现流程，再写成 `component-patterns` skill

## 3.6 `performance-audit`

- 类型：项目越大越值钱的 skill
- 最适合：首屏慢、资源过大、重渲染、列表卡顿、CLS/LCP、图片和脚本加载问题

### 为什么它值得提前准备

前端性能问题常常不是单一 bug，而是组合问题：

1. 打包体积膨胀
2. 图片和字体资源不合理
3. 列表渲染策略太粗
4. 组件更新边界不清楚
5. 关键路径资源加载太晚

所以这类 skill 很适合把排查过程标准化，比如：

1. 先看用户感知问题是什么
2. 再看是不是资源、渲染、交互还是网络问题
3. 再按构建、运行时、页面结构拆开

### 谁最该优先做

1. 中大型前端项目
2. 有性能 KPI 的页面
3. 内容站、活动站、后台首页、复杂仪表盘

## 四、哪些更像 Rule，不要硬写成 Skill

这一点对前端特别重要。

下面这些内容，很多时候**更适合写规则，不适合硬写 skill**：

1. 永久生效的代码风格
2. 统一 import 约束
3. 统一组件目录规范
4. 路由和状态管理底层约束
5. 所有页面都必须有的空态、加载态要求

因为这类内容不是“按需触发任务流程”，而是：

**本来就应该一直生效。**

所以更稳的分法是：

- `AGENTS.md` / `CLAUDE.md` / `Rules`：写长期规范
- Skills：写“前端页面实现”“响应式排障”“可访问性审查”“浏览器验收”这类流程包

## 五、如果主人只想先装一套，怎么选

### 5.1 偏页面交付型前端

优先顺序：

1. `frontend-design`
2. `browser`
3. `responsive-debug`
4. `accessibility-audit`

### 5.2 偏工程型前端

优先顺序：

1. `component-patterns`
2. `responsive-debug`
3. `performance-audit`
4. `browser`

### 5.3 偏组件库 / 设计系统前端

优先顺序：

1. `component-patterns`
2. `accessibility-audit`
3. `browser`
4. `performance-audit`

## 六、我现在最推荐记住的版本

如果主人后面只想记一句不过时的话，我建议记这个：

**前端最值得优先配的，不是“最多字段的 skill”，而是“最能覆盖真实工作流的 skill”：页面实现、真实浏览器验收、响应式排障、组件规范、可访问性和性能复查。**

再说得更短一点就是：

1. 做页面：`frontend-design`
2. 跑页面：`browser`
3. 修布局：`responsive-debug`
4. 统一组件：`component-patterns`
5. 查无障碍：`accessibility-audit`
6. 查性能：`performance-audit`
